# Instrucciones del proyecto

## Producto y alcance

GitHub Profile Generator es un generador visual de README para perfiles de GitHub. Ofrece cinco secciones fijas opcionales: presentación, tecnologías, proyectos, actividad y contribuciones, y contacto, además de secciones personalizadas repetibles con título opcional. Debe servir a personas con distintos conocimientos y niveles de actividad pública. La actividad de GitHub no determina la habilidad de una persona.

La entrega actual incluye la base Next.js, el kit visual bilingüe, `ProfileDocument` versión 2 y un editor de perfil breve con vista previa, copia, descarga y borrador local. `sectionOrder` mezcla referencias fijas y personalizadas; `customSections` contiene párrafos, listas, enlaces, subtítulos, separadores, frases destacadas, imágenes públicas y HTML explícito filtrado, con duplicación independiente, inclusión y eliminación. Actividad y contribuciones reúne aportes manuales y tres tarjetas opcionales de GitHub: calendario, resumen y lenguajes. La consulta pública requiere configuración exclusiva del servidor y una acción explícita; el recorrido manual no necesita cuenta ni credenciales. Las tarjetas exportables requieren un origen público HTTPS que las aloje. Conocimientos, formación y actualidad siguen retirados; se conservan sus estructuras heredadas y referencias internas. Incluye importación local de README mediante pegar texto o abrir `.md`, revisión de secciones propias y confirmación con respaldo del perfil anterior y del Markdown original. No hay asistencia con IA. El HTML solo se interpreta en su bloque explícito y dentro de la política admitida. No presentar una integración sin configurar como servicio habilitado.

## Cómo trabajar

- Comunicar y documentar en español; nombrar código, archivos de código y símbolos en inglés.
- Leer las instrucciones del ámbito afectado, el código existente y la documentación necesaria antes de editar. Los enlaces de este archivo no cargan automáticamente todos los documentos en el contexto de una IA.
- Continuar de forma autónoma dentro del alcance autorizado. Consultar antes de ampliar el producto o introducir decisiones costosas, servicios pagos, nuevas cuentas o dependencias con impacto considerable. Sugerir alternativas con sus motivos.
- Registrar los planes internos en `.private/planning/`, una carpeta local ignorada por Git. Mantenerlos actualizados para cambios que atraviesen varios ámbitos, modifiquen contratos o alteren flujos; evitar planes formales para correcciones locales triviales. No publicar planes, roadmap ni enlaces a estos archivos en commits, issues o pull requests. Si la carpeta no existe en una copia nueva, acordar el alcance con la persona responsable; no asumir que los documentos privados están disponibles.
- Registrar decisiones duraderas con contexto, alternativas y consecuencias en `docs/decisions/`. Revisar la [decisión inicial](docs/decisions/0001-architecture.md) antes de cambiar la estructura.
- Conservar cambios ajenos. No crear commits, hacer push ni desplegar por iniciativa propia.

## Arquitectura y código

- Usar Next.js App Router y TypeScript estricto. Mantener rutas y layouts pequeños; alojar comportamiento en el ámbito que lo posee.
- Mantener inglés como idioma inicial y español como opción real. Usar `next-intl`, rutas `src/app/[locale]` y namespaces de mensajes; evitar textos de interfaz fijos dentro de componentes. Cambiar de idioma conserva la ruta equivalente, usa nombres de idiomas sin banderas y mantiene el atributo `lang` correcto.
- Preferir Server Components. Usar `"use client"` en la frontera más pequeña que necesite estado, eventos o APIs del navegador. Evitar convertir un layout completo en cliente por comodidad.
- Renderizar primero el contenido disponible y aislar esperas independientes. Introducir estados de carga y `Suspense` donde resuelvan una espera real.
- Mantener el modelo, sus reglas y la generación del README en `src/core/`, sin React, Next.js, red, almacenamiento ni secretos. Validar entradas desconocidas con `parseProfileDocument`; las operaciones y `generateReadme` reciben documentos ya válidos. La validación estructural de un borrador no demuestra que sea exportable: respetar los errores del generador, el texto plano y la política de enlaces.
- Derivar vista previa, copia y descarga del mismo Markdown generado. El bloque explícito `html` es la única entrada de HTML interpretada; conservar `skipHtml` para el resto y no crear otra salida del README. Mantener el borrador local fuera de `core`, recuperar y validar antes de habilitar escrituras, y conservar valores inválidos o inaccesibles hasta una decisión explícita del usuario.
- La importación de README usa `src/core/import/`: analizar el AST completo con límites, resolver referencias globales y conservar fuente y rangos antes de dividir. Proponer solo secciones personalizadas con bloques existentes; no inferir módulos fijos ni introducir Markdown crudo. Convertir estructuras complejas mediante la política HTML vigente, informando cambios y errores. La revisión muestra código inerte, sin cargar imágenes ni tarjetas. Pegar, analizar, excluir o cancelar no modifica el perfil. Ver [ADR 0018](docs/decisions/0018-readme-import-with-backup.md).
- Confirmar una importación guarda primero el perfil anterior completo y el Markdown original exacto bajo `github-profile-generator.import-backup.v1`, fuera de `ProfileDocument`. Conservar registros inválidos, la clave v1 y los valores protegidos. Si falla el guardado, exigir una acción explícita para continuar solo en memoria, sin rehabilitar autosave. Invalidar debounce y flush anteriores; descargar ambos respaldos por separado y restaurar con confirmación, conservando el registro. Mantener un único último respaldo; no es un historial ni importación general de JSON.
- El formato actual es v2 con `sectionOrder` y `customSections`; no persistir `moduleOrder` en documentos nuevos. Cada referencia fija y personalizada debe aparecer exactamente una vez. Leer primero `github-profile-generator.profile.v2`; solo si falta, validar y migrar v1 en memoria. No escribir al recuperar, no sobrescribir ni borrar la clave v1 y no usarla como fallback de un v2 inválido. La primera edición guarda v2. Ver [ADR 0013](docs/decisions/0013-custom-sections.md).
- Las secciones personalizadas son instancias independientes, con título opcional y bloques `paragraph`, `list`, `link`, `heading`, `divider`, `quote`, `image` y `html`. El selector ofrece nueve opciones con muestras locales decorativas; agregar no introduce texto de ejemplo. Duplicar copia todos los bloques e ítems con IDs nuevos; ocultar conserva el árbol y eliminar quita solo esa instancia y su referencia. Mantener las ayudas de teclado y conversión de listas limitadas a párrafos y listas del formulario personalizado, sin aplicarlas al código HTML. La ampliación es aditiva dentro de v2, sin cambiar claves, estructuras heredadas ni agregar campos por defecto a los bloques anteriores. Un lector antiguo estricto puede rechazar los tipos nuevos y debe conservar el valor. Ver [ADR 0014](docs/decisions/0014-custom-visual-blocks.md) y [ADR 0015](docs/decisions/0015-explicit-profile-html.md).
- Las imágenes propias se agregan mediante `image` o dentro de un bloque `html` validado, con URL HTTPS de dominio público. `image` exige descripción alternativa no vacía al exportar; HTML exige el atributo `alt` y admite `alt=""` como elección decorativa explícita. La política de URL es sintáctica: rechaza IP, hosts locales, credenciales, fragmentos y puertos no estándar, sin resolver DNS ni verificar disponibilidad. No subir archivos ni aceptar rutas locales, relativas, `blob:` o `data:`. `customImages` contiene pares exactos de URL canónica y alternativa normalizada de los bloques `image`; las imágenes HTML se autorizan dentro de `customHtml`, sin mezclarlos ni persistir metadatos. Cargarlas directamente en el navegador con `loading="lazy"`, `decoding="async"` y `referrerPolicy="no-referrer"`, sin proxy ni optimizador del servidor. Un fallo de carga es efímero y no invalida una URL admitida.
- El bloque `html` guarda exactamente `{ id, type: "html", source }`; conservar la fuente escrita, incluso ante errores, sin sustituirla por el HTML filtrado. `analyzeProfileHtml` es puro y usa AST HAST con esquema explícito: admite HTML de perfiles, alineación y dimensiones acotadas, sin CSS, JavaScript, páginas completas, eventos, identificadores, clases, `srcset`, `picture` ni SVG inline. Los enlaces usan solo HTTP/HTTPS absoluto; relativos y `#anclas` requieren corrección, sin resolverlos contra la aplicación. Mantener avisos por filtrado, límite de 30.000 unidades UTF-16 por bloque, 1.500 nodos, profundidad 32 y presupuesto de 150.000 unidades de HTML visible por documento. Los errores `invalid_html` señalan `source` y bloquean exportación; una sección oculta no participa. `customHtml` es metadato derivado con HTML, árbol HAST permitido y rangos UTF-16 exactos del Markdown final, además de `headingLevel: 3 | 4`; verificar la coincidencia antes de recorrer ese árbol con elementos React permitidos, sin `dangerouslySetInnerHTML`, `rehypeRaw` ni parseo global de HTML. Conservar h1–h6 al exportar y adaptar su nivel semántico solo en la vista previa. No interpretar Markdown dentro de `source` ni prometer paridad con GitHub. Ver [ADR 0015](docs/decisions/0015-explicit-profile-html.md).
- Mantener el recorrido como una presentación personal breve. La introducción permite contar intereses y actualidad sin repetirlos en formularios adicionales. Ofrecer detalles secundarios cuando sean útiles y conservar los datos de borradores anteriores, sin convertir el editor en un CV ni pedir trayectoria para terminar.
- No reintroducir conocimientos, formación o actualidad como opciones, formularios heredados o salida de README. Conservar sus estructuras internas v1 y sus posiciones al editar o reordenar las cinco secciones activas. La validación estructural sigue aplicándose al documento completo, pero el generador no revisa enlaces ni contenido de módulos retirados.
- Distinguir selección, visibilidad y eliminación: configurar una sección no la oculta; ocultar conserva los datos; quitar una entrada los borra de forma explícita. La casilla cambia solo la inclusión y conserva el foco; agregar y editar una sección oculta es una acción identificada. Mantener selección activa, navegación móvil y arrastre como estado efímero, fuera del documento. Al reordenar secciones incluidas, conservar las referencias ocultas, retiradas y de métricas en sus posiciones. Usar claves que distingan referencias fijas de personalizadas; confirmar el orden solo al terminar un movimiento válido y conservarlo al cancelar.
- Actividad y contribuciones usa la referencia fija `contributions` y la inclusión efectiva `visibility.contributions || visibility.metrics`; no ofrecer métricas como sección fija aparte. Ocultar desde la navegación apaga ambos flags; volver a mostrar activa contribuciones y métricas solo si conserva tarjetas seleccionadas. Recuperar un borrador no reescribe flags. Mantener las tres tarjetas desactivadas inicialmente, el bloque de GitHub plegable, los aportes manuales sin usuario y las sugerencias como elecciones explícitas.
- Guardar solo `metrics.username/cards` y los aportes elegidos en sus estructuras heredadas del documento actual. Los snapshots remotos son efímeros, validados y asociados a su usuario; descartar respuestas tardías de otro usuario y distinguir ceros reales de fallos. El formulario no consulta automáticamente al montar, recuperar, abrir el bloque o escribir un usuario. Las imágenes de tarjetas seleccionadas sí solicitan actividad al mostrarse.
- El servidor admite un PAT classic dedicado y verifica `x-oauth-scopes` presente, vacío o exactamente `public_repo` antes de consumir datos. Preferir únicamente `public_repo` para las consultas GraphQL de repositorios públicos; no sumar `repo`, `read:user` ni otros scopes. Rechazar credenciales no verificables, incluidos tokens fine-grained. El cliente solo ejecuta consultas de lectura aunque el scope público permita otras operaciones. Mantener `GITHUB_TOKEN` fuera de Git y del navegador. `APP_URL` es un origen HTTPS público configurado, nunca derivado del Host. Sin él, `generateReadme` permite revisar el mismo Markdown con rutas locales y devuelve `exportIssues: activity_not_configured`; copia y descarga permanecen deshabilitadas hasta desmarcar tarjetas o configurar un host público. Ver [ADR 0010](docs/decisions/0010-github-activity.md).
- Ofrecer tecnologías mediante el catálogo local curado, autocompletado, chips con iconos y una alternativa de texto propio. Sugerir categorías editables al agregar, respetar el destino elegido y no reagrupar borradores al recuperarlos o cambiar de idioma. Organizar por categoría es una acción explícita; quitar un título conserva sus herramientas. Mantener sus estructuras heredadas, IDs opacos, orden y contextos. Los iconos proceden de Devicon, Simple Icons y Lobe Icons fijados a commits, con SVG locales y atribución. Exportar iconos decorativos de 20 × 20 junto al nombre visible y mantener compatibilidad de vista previa con el marcado anterior de 32 × 32. Una herramienta de IA en el catálogo no implica una integración con IA.
- En contacto, agregar primero la entrada y luego elegir dentro proveedor, web propia o correo y URL. Enfocar el selector al agregar, conservar foco al elegir y avanzar con Tab. Permitir repeticiones y mantener un único botón de agregar. Resolver el icono por la URL validada y los dominios explícitos, nunca por la etiqueta o la selección efímera; conservar `links` v1 sin proveedor adicional. Cambiar selección no sustituye URL o nombre. Los iconos son decorativos de 20 × 20 y la etiqueta personalizada es opcional. Mantener la normalización y los errores compartidos.
- Ubicación es opcional y conserva texto libre. Ofrecer países EN/ES y banderas de `core/location`, con elección explícita por combobox. Guardar el prefijo Unicode y nombre en `location` v1; generar únicamente SVG decorativo de 20 × 15 desde el catálogo de flag-icons fijado. No usar geolocalización, inferir países de ubicaciones anteriores ni traducir el texto guardado al cambiar la interfaz. Mantener tokens exactos de imagen, copias locales y licencia MIT.
- No interpretar HTML ni sintaxis de imagen escrita dentro de los campos de texto ordinarios. Reconocer los tokens de iconos permitidos, las rutas exactas de tarjetas propias, las imágenes de `customImages` y las unidades completas verificadas de `customHtml`; mantener la lista del renderizador y `skipHtml` para todo lo demás, sin `rehypeRaw`. Los SVG de actividad son pasivos, escapados y sin recursos externos; no aceptar un host o imagen arbitrarios para esas tarjetas. No agregar niveles de habilidad, rankings de herramientas ni inferir trayectoria. Los enlaces de contenido admiten HTTP/HTTPS según la política web; `mailto:` solo se admite en contacto. Registrar las fuentes y las marcas compartidas de familia en [recursos de terceros](THIRD_PARTY_NOTICES.md).
- Reservar `src/modules/` para las secciones del perfil; `src/components/ui/` para primitivas visuales reutilizables. No confundir módulos de producto con componentes genéricos.
- Mantener credenciales y clientes de servicios en `src/server/` con `server-only`. Validar entradas en cada frontera; ninguna clave secreta usa `NEXT_PUBLIC_`.
- Reutilizar tokens y primitivas del kit visual. Mantener navegación por teclado, etiquetas, foco visible, contraste y estados de error claros.
- El kit visual es interno: `/design-system` solo funciona en desarrollo y debe responder 404 en producción, sin enlaces públicos. Playwright (`pnpm test:e2e:ui`) es una herramienta del repositorio. No presentar Storybook como instalado ni sumar un taller nuevo sin acordar sus dependencias.
- La navegación del editor muestra siempre las secciones en una sola fila horizontal con scroll interno, casillas, selección y tiradores. Conservar foco al seleccionar o incluir, mostrar horizontalmente el elemento activo/enfocado sin saltos verticales y ofrecer izquierda/derecha para ordenar la sección activa. Mantener proyección temporal, confirmación al soltar y Escape para cancelar el arrastre. El selector de bloques sigue plegable. Revisar alturas de teléfono, llegada a campos y desbordamiento local, sin ensanchar la página. Ver [ADR 0017](docs/decisions/0017-horizontal-section-navigation.md).
- Preferir funciones y componentes directos. No agregar repositorios, contenedores de inyección, clases base o capas sin una necesidad concreta. No agregar `useMemo` o `useCallback` por reflejo: justificar su necesidad con comportamiento o medición.

## Verificación

Usar los scripts de `package.json`: `pnpm dev`, `pnpm build`, `pnpm start`, `pnpm lint`, `pnpm typecheck`, `pnpm format`, `pnpm format:check`, `pnpm docs:check`, `pnpm test`, `pnpm test:watch`, `pnpm test:e2e`, `pnpm test:a11y` y `pnpm check`.

Elegir verificaciones según el cambio y agregar pruebas de comportamiento cuando protejan contratos o recorridos relevantes. No agregar pruebas que repitan la implementación. Antes de cerrar, revisar el diff, ejecutar los controles pertinentes y distinguir resultados ejecutados de verificaciones pendientes. No afirmar que una revisión automática demuestra accesibilidad completa.

Para móvil, comprobar también alturas de teléfono, llegada al primer campo y uso desde una edición larga. `toBeVisible()` no garantiza que un control esté dentro del viewport y Playwright puede desplazarlo automáticamente antes de interactuar. Las capturas iniciales y las medidas de alcance se toman antes de usar `scrollIntoView`, clic o escritura sobre el campo evaluado. Distinguir emulación de un teléfono y prueba en dispositivo físico.

## Delegación

Los roles están en `.codex/agents/`. Delegar únicamente trabajo independiente con objetivo, archivos propietarios y criterios claros. Evitar escrituras paralelas sobre los mismos archivos y coordinar los cambios a dependencias, configuración y contratos compartidos. El agente principal integra, revisa diffs y valida el resultado completo. Los roles de lectura no editan archivos ni ejecutan acciones que alteren el proyecto.

Para tareas autorizadas de commit y push, delegar en el rol `release` de `.codex/agents/release.toml`, con **GPT-5.6 Luna** (`gpt-5.6-luna`, esfuerzo `medium`), por preferencia explícita del usuario. Si la herramienta de delegación requiere seleccionar el modelo por separado, indicarlo expresamente. No sustituirlo silenciosamente si no está disponible. El principal revisa el alcance y las verificaciones antes de publicar; el rol conserva permisos de la sesión y esta preferencia no autoriza commits o pushes por iniciativa propia.
