## Reproducible dependency inventory

After installing the pinned dependency tree:

```sh
pnpm install --frozen-lockfile
pnpm licenses:generate
pnpm licenses:check
```

These commands use [scripts/check-licenses.mjs](../scripts/check-licenses.mjs), without adding a third-party tool. The inventory walks package roots in `node_modules` and pnpm's virtual store, resolves local links without following loops, and groups results by name and version. It includes transitive dependencies, development tools, and optional packages present for the installed platform. It reads each package's declared license and provenance from its `package.json` and preserves complete license and notice files found in each package. Packages without a notice at their root require a reviewed resolution for their exact name and version; a license or rights holder is not inferred from a package name.

- `licenses:generate` writes `public/licenses/dependencies.txt`, suitable for distribution, without variable dates or absolute machine paths.
- `licenses:check` verifies required notices and that the public inventory matches the installed tree; it does not modify the public file.
- Both commands leave a local report in `work/oss/dependency-licenses.json`, ignored by Git, containing names, versions, licenses, provenance, relative original-file paths, hashes, notices, warnings, and issues. It also includes the lockfile hash and platform. It does not read environment files or credentials.
- The check fails if license metadata is missing or unresolved, required dependencies are not installed, required notices are missing, copies of font or Lucide licenses differ from the installed packages, a package's variants have conflicting licenses, or the inventory is out of date. It also fails if an exact resolution is missing for a package without a root notice, an evidence file changes, or the reviewed npm integrity differs from the lockfile.

### Linux finding

The first clean CI installation found `@img/sharp-libvips-linux-x64@1.3.4` without a root notice, a variant that was not installed on Windows. Its [official npm artifact](https://registry.npmjs.org/@img/sharp-libvips-linux-x64/1.3.4) declares `LGPL-3.0-or-later`. The catalog records the exact lockfile integrity and original evidence for that version, the upstream third-party notices, and supplemental terms preserved without changing their license or attribution.

Reviewing this package's notices does not certify that all components of its native library are covered or replace the obligations for a specific binary redistribution. A successful Windows build does not show that another platform has complete notices; CI and Vercel therefore regenerate and verify the inventory on Linux before the build.

The report reflects files actually installed, so an installation with leftover packages may include more than necessary. To prepare a distribution, start with a clean lockfile-based installation and regenerate the inventory on the target environment. Changing the operating system or architecture may change optional packages and requires regenerating the inventory and reviewing the diff. This process alone does not verify the license or contents of the remote registry, legal compatibility among all terms, whether maintenance is current, or the exact contents of a bundle.

## Preparing a distribution

Publishing the source repository and distributing a bundle, container, or binary are separate releases. For a specific distribution:

1. Keep `LICENSE`, `THIRD_PARTY_NOTICES.md`, and the complete notices for every copied resource. Retain attribution headers or comments in adaptations.
2. Install from the lockfile, regenerate the inventory on the target platform, and resolve unknown license or provenance cases. Review which packages reach the browser, server, and artifact tools. The complete inventory is conservative: it does not prove that every listed package is included in the output.
3. Include required notices in the distributed artifact. For Next.js, keep `public/licenses/` and the license files accompanying icons and flags; when preparing a `standalone` output or container, explicitly verify that these files are copied and accessible. Also include the project license and any additional sources or notices required for each redistributed component.
4. Review components with additional terms. For example, the Windows tree includes `@img/sharp-win32-x64` with `Apache-2.0 AND LGPL-3.0-or-later`, as well as licenses for internal libraries; there are also MPL-2.0 packages and CC-BY-4.0 data. Keeping their texts does not replace any applicable source-access, modification, attribution, or binary-redistribution conditions. For the specific artifact, review the [sharp project](https://github.com/lovell/sharp), [sharp/libvips binary licenses](https://github.com/lovell/sharp-libvips), and the [official MPL FAQ](https://www.mozilla.org/en-US/MPL/2.0/FAQ/).
5. Keep credentials, personal data, and local environment files out of the distribution. Review trademarks and user-contributed content separately from code licenses.

No verifiable container or binary package is published here yet. The inventory prepares notices and surfaces decisions that remain for each distribution; it does not certify compliance for artifacts that have not been produced or platforms that have not been installed.

## Updating resources and maintenance

Before adding a library or integration, verify in its official repositories or documentation that it is still maintained and has not been archived or announced as unmaintained. Evaluate its license and those of relevant resources and dependencies. Do not assume that a fork has the same maintenance status or terms as the original project.

For a local adaptation, record the repository, commit or version, and source files; retain original texts and describe what changed. When updating it, review upstream differences and notices, update pinned links, and regenerate the inventory. GitHub Stats Extended retains its pinned revision even though the adaptation runs on our server. Adaptations do not receive upstream changes automatically and do not imply endorsement by their authors.
