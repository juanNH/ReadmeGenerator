# Repository guardrails

## Branch policy in CI

The branch-name check runs before the rest of `Quality` and publishes the stable `Branch policy` status. For pull requests, it reads the actual source branch name from `GITHUB_HEAD_REF`, including for fork branches; it does not infer the name from `refs/pull/.../merge`. The job checks out each pull request's base SHA before locating the validator and never loads that script from the pull request's head branch, including for a `dev`-to-`main` promotion. If the P04 script is already present on the base, the job runs that copy. The initial-promotion exception is derived from event data and allows only a same-repository `dev`-to-`main` promotion; the job does not check out `dev` to run its version of the validator.

The policy checks branch prefixes and naming syntax. It does not determine whether a branch description is written in English, and it does not validate commit messages. Use English for new branch names and commit messages as described in the [branching guide](branching.md).

Only pull requests authored by `dependabot[bot]` bypass the branch-name convention, and they must target `dev` or `main`; the actor who opened, updated, or reopened the pull request does not change that decision. P04 sets `target-branch: dev` for the npm and GitHub Actions entries in `.github/dependabot.yml`. GitHub reads this file from the default branch ([Dependabot documentation](https://docs.github.com/en/code-security/concepts/supply-chain-security/about-the-dependabot-yml-file#where-to-store-the-dependabotyml-file)), so version and security updates continue to target `main` until the setting reaches the default branch. Afterwards, version updates target `dev`, while security updates continue to target the default branch. Review security-update pull requests as production hotfixes against `main`, then bring the fix back to `dev` in a separate pull request. Other bots must use a conforming branch name. The `dev`-to-`main` promotion is also explicitly allowed. Pushes to `main` or `dev` are not treated as work branches, and pushes to existing branches are not revalidated retroactively. Before requiring the new status, review open pull requests and add only their numbers to `grandfatheredPullRequestNumbers` when their published branch names do not comply. The list starts empty; new branches must pass the check when a pull request is opened.

The workflow uses the `pull_request` event, read-only permissions, and checkout without persistent credentials. It does not use `pull_request_target`, secrets, or dependency installation to validate branch names. Although the job reads policy code from the base SHA, GitHub runs the workflow definition associated with the pull request's merge ref ([`pull_request` event documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request)). A pull request can also modify or remove `.github/workflows/ci.yml`. The policy helps prevent accidental naming mistakes; it is not protection against a malicious workflow change. Treating it as a security control requires trusted review of workflow changes and independent enforcement, such as a required workflow sourced from the base or repository rules. That enforcement is still pending and is not enabled by these files. The test suite covers fork pull requests, invalid branch names, Dependabot targeting `dev` and `main`, the `dev`-to-`main` promotion, and push events to integration branches.

In the first pull request that introduces this check, the base commit does not yet contain the P04 policy script. For ordinary branches, the bootstrap imports only the shared P03 validator from that base checkout; if the base does not contain the validator, the check fails closed. The bootstrap itself verifies the exact first-promotion exception for a same-repository `dev`-to-`main` pull request and the Dependabot exception for `dev` or `main`. P04 context and integration tests run in the quality job against the merge ref, alongside the other checks. After P04 is merged, the early job uses the complete script from the base SHA.

## Pending administrative protection

The workflow does not change GitHub repository settings. Configure rules for `main` and `dev` that require pull requests and prevent force-pushes and branch deletion. When enabling required checks, select the `Branch policy` status and the `Check, build and browser accessibility` quality job shown in Actions. Do not require approval from another person while there is only one maintainer; keep any emergency bypass limited and identifiable. Confirm and record the settings in GitHub before describing branch protection as active.

The existence of this file or workflow does not prove that administrative settings are applied. Until they are configured in GitHub, CI reports the check result but does not itself prevent a merge.
