# Controles del repositorio

La verificación de nombres de ramas se ejecuta antes del resto de `Quality` y publica el estado estable `Branch policy`. En solicitudes de cambio usa el nombre real de origen (`GITHUB_HEAD_REF`), también para ramas de forks; no deduce el nombre desde `refs/pull/.../merge`. El job hace checkout del SHA base de cada PR antes de buscar el validador y no obtiene el script desde la rama `head`, incluida la promoción `dev`→`main`. Si el script P04 ya existe en la base, ejecuta esa copia. La excepción de primera promoción se resuelve desde los datos del evento y solo admite `dev`→`main` del mismo repositorio; no hace checkout de `dev` para ejecutar su versión del validador.

Solo las solicitudes cuyo autor es `dependabot[bot]` se admiten sin aplicarles la convención de ramas y deben tener `dev` o `main` como destino; el actor que abrió, actualizó o reabrió el PR no cambia esa decisión. El cambio P04 configura `target-branch: dev` en las entradas npm y GitHub Actions de `.github/dependabot.yml`. GitHub lee este archivo desde la rama predeterminada ([documentación de Dependabot](https://docs.github.com/en/code-security/concepts/supply-chain-security/about-the-dependabot-yml-file#where-to-store-the-dependabotyml-file)), así que las actualizaciones de versión seguirán apuntando a `main` hasta que ese cambio llegue a la rama predeterminada; después apuntarán a `dev`. Las actualizaciones de seguridad siguen apuntando a la rama predeterminada (`main` actualmente); se revisan como hotfix de producción y su corrección debe volver a `dev` mediante otra solicitud de cambio. Otros bots deben usar un nombre conforme. La promoción de `dev` a `main` también está permitida explícitamente. Los pushes a `main` o `dev` no se interpretan como ramas de trabajo, y los pushes a ramas existentes no se vuelven a validar con efecto retroactivo. Antes de exigir el nuevo estado, revisar las solicitudes ya abiertas y agregar únicamente sus números al conjunto `grandfatheredPullRequestNumbers` si sus ramas publicadas no cumplen la convención. La lista comienza vacía; las ramas nuevas deben pasar el control al abrir una solicitud.

El workflow usa el evento `pull_request`, permisos de solo lectura y checkout sin credenciales persistentes. No usa `pull_request_target`, secretos ni instalaciones de dependencias para validar el nombre. Aunque el job consulta la policy desde el SHA base, GitHub ejecuta la definición del workflow asociada al merge ref del PR ([documentación del evento `pull_request`](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request)). Un PR también puede modificar o quitar `.github/workflows/ci.yml`, por lo que esta policy ayuda a evitar errores accidentales de nombres; no es una defensa frente a un cambio malicioso del workflow. Para tratarla como un control de seguridad hace falta una revisión confiable de esos cambios y un enforcement independiente, como un workflow requerido desde la base o reglas administrativas del repositorio. Ese enforcement sigue pendiente y no queda activado por estos archivos. La suite cubre solicitudes desde forks, ramas inválidas, Dependabot dirigido a `dev` y `main`, la promoción `dev` a `main` y los eventos de push a ramas de integración.

En el primer PR que introduce este control, el commit base todavía no contiene el script de política de P04. El bootstrap importa únicamente el validador compartido de P03 desde ese checkout base para las ramas ordinarias; si la base no incluye el validador, falla de forma cerrada. La excepción exacta para la primera promoción del mismo repositorio (`dev`→`main`) y la excepción de Dependabot hacia `dev` o `main` se comprueban con el código del bootstrap. Los tests de contexto e integración de P04 se ejecutan en el job de calidad sobre el merge ref, junto con el resto de los controles. Después de integrar P04, el job temprano usa el script completo desde el SHA base.

## Protección administrativa pendiente

El workflow no modifica la configuración de GitHub. En la configuración del repositorio, establecer reglas para `main` y `dev` que exijan solicitudes de cambio y protejan contra force-push y borrado. Al habilitar checks requeridos, seleccionar el estado `Branch policy` y el job de calidad `Check, build and browser accessibility` que aparecen en Actions. No exigir una aprobación de otra persona mientras haya una sola mantenedora; conservar un bypass de emergencia limitado e identificable. Confirmar y registrar en GitHub la configuración aplicada antes de declarar activa la protección.

La configuración administrativa no queda demostrada por la existencia de este archivo o del workflow. Mientras no se aplique en GitHub, el estado de CI solo informa el resultado del control y no impide por sí mismo un merge.
